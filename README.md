## Builderr Signalpost Submission Manifest

- **1,000+ Company Profiles:** `db/profiles_1000.json` (1,050 real Brreg records) and `db/init.sql` (matching SQL INSERTs). Generated by `python scripts/fetch_1000_brreg.py`, or by the `seed-1000-profiles` GitHub Actions workflow. Each record carries `source_url`, a UTC `fetched_at` timestamp, a deterministic SHA-256 `delta_sync_hash`, and `revenue_nok` / `ebitda_nok` = `null` (withheld without proof).
- **Repository Link:** https://github.com/Pavan3030-pr/PRATIV
- **One Command to Run (revision 2):** `./run.sh numbers.txt [results.jsonl]` reads a file of organisation numbers (one per line) and writes one JSON result per company, in input order (default `output/results.jsonl`). Older forms still work: `./run.sh` (needs only Python 3 and internet; runs the agent on 100 random companies and writes `output/results.jsonl` + `output/summary.json`). Specific companies: `./run.sh --numbers 923609016 984851006`. HTTP API only: `docker compose -f docker-compose.agent.yml up --build`. Full stack with UI and backend (needs OAuth/JWT secrets): `docker compose up --build`.
- **Model / API Details:** Brønnøysund Register Centre Open API (`data.brreg.no`), Brreg Regnskapsregisteret open API (annual accounts), Python/FastAPI agent (`agent/core.py`), Spring Boot backend, PostgreSQL (the `pgvector` extension and a `vector` column are installed for future embeddings and are not populated by the current agent). The agent makes no LLM call, so no LLM model is used at runtime.
- **Expected Run Costs:** Brreg is free, and no LLM tokens are consumed by the current code. The agent uses at most 4 registry requests per company plus at most 10 website requests when the registry lists a site (about 1,400 for a 100-company daily test), well inside the 2,000-request and 45-minute limits. A per-run request budget (default 1,900, retries included, `SIGNALPOST_REQUEST_CAP`) is enforced in `agent/core.py`; requests are throttled to about 12 per second.
- **Signalpost website:** https://prativ.vercel.app/#/explore (public, no login: search 1,095 crawled companies or any other Norwegian company through a live register lookup, open one, check each fact's source, compare two, export CSV/JSON).
- **Live demo without a backend:** https://prativ.vercel.app. Use "Enter Evaluator Workspace"; if `localhost:8080` is unreachable, lookups query Brreg directly from the browser and compute the SHA-256 hash with `crypto.subtle`.

## Website, social, news and jobs rules (audit fixes)

- **Own website only.** The registry website is fetched (public hosts only, max 10 requests per company) and must both look like this company's own domain (the host shares a distinctive word with the legal name) and show this company's organisation number or its exact registered name on the home page or its contact/about/privacy pages. A parent-group, sister-company or brand site fails, is reported as `website.status = not_verified`, and no social links, news or jobs are taken from it. An unreachable site is reported in `missing_fields.website` and is **not** published as the company's website: the registry's `hjemmeside` value alone is never asserted as a fact when website enrichment is on.
- **Social links.** Only accounts whose handle equals the company's legal name (with or without AS/ASA) or its own verified domain are published. Group, web-agency, theme, share-button and personal-profile links are discarded and listed in the explainability log.
- **News.** Only real posts: own page on the verified site, human title (menu labels such as "See more news" and product/service pages are rejected), and a publish date from `time[datetime]`, JSON-LD `datePublished`, RSS `pubDate` or Atom `published`. "modified"/"updated" dates, `dateModified`, `lastBuildDate` and Atom `<updated>` are never used. Up to 5 newest items, each with its own evidence record.
- **Jobs.** Careers / "ledige stillinger" pages are reached from links on the verified site, then from the site's `sitemap.xml` when no link exists (common paths such as `/karriere` are the last fallback). Postings are read from schema.org `JobPosting` JSON-LD, from posting links on the page, from employer-scoped job-board pages the company itself links to (FINN employer pages, Jobbnorge employer search) and from the employer's own Workday tenant when the site links it. A posting needs a human role title, a same-site or recognised recruitment-service URL, and must not be site navigation, a menu label, a culture/FAQ card or an "open application" link; a `time` element next to it becomes `posted_at`, otherwise the item is reported as an open posting. Up to 8 items, each with its own evidence record; one vacancy advertised on two boards is one row, while two identical titles on the same board stay separate roles. Nothing is guessed.
- **Jobbnorge employer postings.** Jobbnorge's search page is a JavaScript shell and lists nothing when fetched as HTML, so postings are read from the public JSON feed its own search page calls (`publicapi.jobbnorge.no/v3/jobs`), with one cached request per 15 minutes for a whole run. The employer is matched by the `employer=` link on the company's site when there is one (stronger), otherwise by an **exact match of the registered name**, ignoring legal form and word order (`NORGES TEKNISK-... UNIVERSITET NTNU` = `NTNU - Norges teknisk-... universitet`). An extra word in the employer name is never accepted. Because the proof is the employer record on Jobbnorge, these postings are published even when the company's own site cannot be verified or reached; the page states which match was used. Verified examples: NTNU (8), Universitetet i Oslo (8), Kongsberg Gruppen (8 on its own site), Universitetet i Stavanger (2), USN (2), OsloMet (2).
- **Workday careers tenants.** Employers that run their own Workday site (equinor.com/careers -> equinor.wd3.myworkdayjobs.com/EQNR) publish only in a JavaScript page, so the crawler reads the tenant's public job feed — the JSON that page itself calls. Each posting's title, location, country and publish date come from the tenant's own record for that posting, not from relative text such as "Posted 3 Days Ago". A tenant is read only when the company's verified site links it and the tenant host carries the company's name, so a parent group's or an agency's tenant is never attributed to this company, and only postings whose record names Norway are published. Verified live: Equinor ASA shows 8 dated Norwegian postings.
- **SuccessFactors career sites.** Employers whose vacancies sit on a SuccessFactors career site (yara.com/careers -> jobs.yara.com) get a landing page of categories only; the postings are rendered on that site's own country search (`/search/?q=&locationsearch=Norway`). The crawler reads that search page when the company links the host and the host carries the company's name, and takes the title, location and posted date from the listing row. Only rows whose own location is Norwegian are published. Verified live: Yara International ASA shows 8 dated Norwegian postings.
- **Group careers pages.** Some groups publish all vacancies on a shared careers site instead of the subsidiary's own host (telenor.no/om/jobbitelenor -> telenor.com/career/open-positions). That page is followed only when its host carries a distinctive word of the registered name, and only vacancies whose card names a Norwegian unit of the group are attributed to the company ("Customer Service Advisor" under "Telenor Danmark" is not Telenor ASA's posting). Each item states the hiring unit it was read from.
- Run `./run.sh numbers.txt --no-web` for registry-only mode. After `--web-deadline` seconds (default 1800) remaining companies are processed registry-only so the 45-minute limit holds.

## What the agent returns for a company number

Per company (`./run.sh`, or `POST /api/v1/crawl/{orgnr}`): legal name, organisation form, address, founding date, industry (NACE), registered employees, website (only after ownership is verified), VAT status, institutional sector, bankruptcy/liquidation status, general manager, board chair and board size, number of sub-units, latest annual-accounts revenue, operating result and net result with period and currency, and open or dated job postings linked from the company's own site. Every fact has its own evidence record: exact source URL, JSON field path, SHA-256 of the value, retrieval timestamp and an explanation. A fact that is not in the source stays null with a reason in `missing_fields`; nothing is estimated or derived (EBITDA is intentionally not reported).

**Matching safeguards:** Modulus 11 check digit, the response's organisation number must equal the request, accounts must belong to the requested company, and sub-units must name it as parent. Foreign records are discarded and reported in `match_checks`.

**Summary:** the summary opens with one buyer-relevant fact and its source — filed revenue (Regnskapsregisteret), an open role with its URL (the company's verified site) or the registered industry/employees (Enhetsregisteret) — instead of restating registry fields. The rest of the summary adds status, leadership and the latest dated news; every sentence is traceable to a fact with its own evidence record.

**CI:** every push runs the agent tests, the Spring Boot tests on Java 21, the frontend lint and production build, and the explorer data checks.

**Security and operations:** the agent API sends an `X-Request-ID` on every response, returns JSON errors with that id, enforces a per-client request budget (`SIGNALPOST_RATE_LIMIT_PER_MIN`, default 300; health probes exempt) and only allows browser calls from origins listed in `SIGNALPOST_ALLOWED_ORIGINS` (empty by default). Server-to-server callers are unaffected. Both containers run as non-root users, the agent image has a health check, and every required setting is documented in [.env.example](.env.example).

**Update detection:** `delta_sync_hash` covers the 7 core registry fields, identical to `db/profiles_1000.json`, so a stored profile and a live crawl are directly comparable. `content_hash` covers the full profile. Each result carries `update.status` (`new`, `unchanged`, `changed`) and the exact `changed_fields` (old and new values). A secondary source being temporarily unreachable is reported as unavailable and never counted as a change. `./run.sh --all` refreshes every seeded company and writes `db/profiles_enriched.json`.

Tests: `cd agent && python -m unittest -v test_main test_web` (offline, no network needed). Frontend: `npm test` (Vitest), `npm run e2e` (Playwright, including an axe scan of every explorer page that fails on any serious or critical WCAG 2.1 AA violation). Current committed explorer: **1,095 profiles**, 52 with a verified website, 17 with 112 job postings, 12 with 52 dated news items, 430 with filed annual accounts.

## 1. Executive Summary & Architecture Overview

SIGNALPOST is a source-first company research application. It retrieves organization identity fields from Norway's Brønnøysund Register Centre (Brreg), stores profile and evidence records, and exposes the agent and audit trail through a compact operations workspace.

## Public explorer (Signalpost website bonus)

Open `/#/explore`: find a company, open it, check each fact against its source, compare two. No login.

- **Nothing is reported missing just because it is not in the crawl.** A search that matches no crawled profile asks Enhetsregisteret live (public, CORS-enabled API; same source the agent reads) and lists real register matches. Opening one shows a clearly labelled **registry-only** record: legal name, form, address, founding date, employees, industry, status and website, each read in that request with its retrieval time and SHA-256.
- **How it works** (`/#/explore/about`) states where every kind of fact comes from, the ownership rule for websites, what is never shown, and the known limits.
- **Honest failure states**: a failed register lookup says so instead of implying no company exists; a missing dataset document falls back to the register; an unreachable source is reported as unreachable.

Crawler behaviour: `/robots.txt` is fetched once per host and honoured — a disallowed path is skipped and logged, never fetched.
Data: `python3 scripts/build_explorer_data.py`. Smoke test: `node scripts/smoke_explorer.mjs [site-url]`.
